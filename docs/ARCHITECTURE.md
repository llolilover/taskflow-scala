# TaskFlow — архитектура и обоснование решений

## Бизнес-сценарий

TaskFlow управляет задачами и их жизненным циклом: от списка запланированных задач до выполнения или отмены. Для учебного проекта ключевые требования — **соблюдение правил переходов статуса**, **защита изменений при конкурентных запросах** и **аудит успешных переходов**.

Это целенаправленно небольшой монолитный HTTP-сервис, а не набор микросервисов. Наблюдаемых метрик нагрузки или реальных пользователей у учебного проекта нет.

## Слои приложения

```text
HTTP клиент
    |
    v
TaskRoutes                 http4s: маршруты, JSON DTO, 400/404/409
    |
    v
TaskOperations             интерфейс прикладных операций
    |
    +---- PostgresTaskRepository   Doobie: SQL и транзакции
    |              |
    |              v
    |         PostgreSQL 16        tasks, task_history, flyway_schema_history
    |
    +---- TaskService             Ref: только быстрые unit-тесты

Task + TaskRules           чистые правила, независимые от HTTP/БД
Main                       инициализация Flyway, БД, сервера
```

Вся логика жизненного цикла задачи сосредоточена в чистых функциях предметной модели. HTTP-слой переводит запросы в параметры операций и ошибки в коды ответа. Репозиторий отвечает за атомарность хранения.

## Доменная модель и состояния

- `TaskId` и `UserId` — разные Scala 3 `opaque type` поверх UUID: компилятор не позволяет случайно перепутать идентификаторы.
- `TaskStatus` — `enum`: `Backlog`, `InProgress`, `Done`, `Cancelled`.
- `DomainError` — ADT: `NotFound`, `Validation`, `InvalidTransition`, `VersionConflict`.
- `Task.create` проверяет название: обрезает пробелы, запрещает пустую строку и длину больше 120 символов.
- `Task.transition` применяет правила статусов и увеличивает версию только при разрешённом переходе.

Допустимые переходы:

| Откуда | Куда |
| --- | --- |
| `Backlog` | `InProgress`, `Cancelled` |
| `InProgress` | `Backlog`, `Done`, `Cancelled` |
| `Done` | — (терминальное состояние) |
| `Cancelled` | — (терминальное состояние) |

## Конкурентные изменения и история

Запрос `PATCH /tasks/{id}/status` передаёт `expectedVersion` — версию, которую клиент видел ранее.

В рамках **одной транзакции PostgreSQL**:

1. Читаем задачу, возвращаем `404`, если она отсутствует.
2. Сравниваем ожидаемую и текущую версии; старое значение даёт `409`.
3. Проверяем переход чистой функцией `Task.transition`.
4. Выполняем условный SQL UPDATE по `id` и `version`.
5. Если изменена ровно одна строка — записываем переход в `task_history`; иначе `409`.
6. PostgreSQL коммитит UPDATE и INSERT вместе либо откатывает оба.

```sql
UPDATE tasks
SET status = :next_status, version = version + 1, updated_at = now()
WHERE id = :task_id AND version = :expected_version;
```

Важен **пункт 4**, а не только предварительная проверка в пункте 2. Два запроса могут прочитать одну версию одновременно; условный UPDATE не даст обоим перезаписать её. Параллельный тест проверяет ровно одного победителя и ровно одну запись истории.

Запретить переход статуса на уровне чистой функции проще тестировать, чем смешивать эти правила с SQL.

## Постоянное хранение

- `tasks`: UUID, название, исполнитель (опционально), статус, версия и отметки времени.
- `task_history`: запись каждого успешного перехода, связанная с задачей внешним ключом.
- `Doobie ConnectionIO`: описание SQL-программы; `.transact(xa)` запускает её в транзакции.
- `HikariCP`: повторно использует соединения и ограничивает количество одновременных соединений.
- `Flyway`: запускает версии схемы `V1` и `V2` до открытия HTTP-порта.

При ошибке миграции сервер не стартует, что лучше, чем незаметное обращение к несовместимой схеме. `FLYWAY_BASELINE_ON_MIGRATE=true` нужен только для **проверенной старой локальной БД** из предыдущей версии проекта.

## Фильтрация и пагинация

`GET /tasks` принимает `status`, `assignee`, `limit` (1–100) и `cursor` (UUID). Возвращает `items` и `nextCursor`.

Вместо `OFFSET` используется keyset-предикат `id > cursor` и `LIMIT (limit + 1)`. Дополнительная строка позволяет понять, существует ли следующая страница, без отдельного подсчёта всех записей.

**Компромисс:** сортировка по UUID (индекс первичного ключа) стабильная, но **не соответствует времени создания**. При одновременных изменениях фильтруемых статусов страницы не являются согласованным снимком. Для продакшен-ленты по хронологии можно перейти к курсору `(created_at, id)`.

## Локальный запуск и сеть

`docker compose up -d --build` поднимает PostgreSQL и HTTP-приложение. Приложение внутри Docker слушает `0.0.0.0:8080`, но Docker публикует его только на `127.0.0.1:8080` хост-компьютера. При самостоятельном `sbt run` интерфейс по умолчанию — `127.0.0.1`; переменная `TASKFLOW_BIND_ALL=true` используется для контейнера.

Настройки БД передаются через `DB_URL`, `DB_USER`, `DB_PASSWORD`. Пароль в демонстрационном Compose **не предназначен для production**.

## Проверки

- **Домен:** статусы, ошибки и валидация без инфраструктуры.
- **HTTP:** декодирование JSON, валидация, коды 201/200/400/404/409 и пагинация.
- **PostgreSQL:** отдельные транзакции, история, запрещённые переходы, конкурентные обновления и повторный запуск Flyway.
- **End-to-end:** сборка JAR, сборка Docker-образа, реальный HTTP smoke-тест и проверка сохранности задачи/истории после перезапуска контейнера.

Сценарии ручного запуска см. в [TESTING.md](TESTING.md).

## Осознанные ограничения

- Нет аутентификации, авторизации, ролей и отдельной таблицы пользователей: `assigneeId` — внешний UUID без проверки существования пользователя.
- Нет редактирования названия или исполнителя после создания.
- Нет полноценной пагинации истории и поиска по названию.
- Нет распределённой очереди и внешних интеграций — поэтому нет причин внедрять Kafka или Outbox.
- Нет доказанных нагрузочных характеристик и production-SLA.
- Нет production-управления секретами, централизованного мониторинга и публичного деплоя.

Эти ограничения намеренные: цель проекта — продемонстрировать понятный, воспроизводимый backend с корректностью данных, а не искусственно добавить максимум технологий.
